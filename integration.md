# Contributing and integration workflow

Anyone can contribute: bug reports, fixes, tests, documentation, data-source work, new features. You do not need to
ask permission to start. Please read this page once; it keeps reviews quick and the history readable.

> **The short version:** branch from `integration`, open the pull request **against `integration`** (never `main`),
> write a failing test first, use a Conventional Commit title, fill in the PR template, add labels.

## Branches

| Branch | Purpose | Who merges into it |
|---|---|---|
| `main` | Stable, released code. Always passes all tests. | Maintainers only, by promoting `integration`. |
| `integration` | Where all work lands and is tested together. **Every pull request targets this branch.** | Maintainers, after review. |
| `feat/…`, `fix/…`, `docs/…`, `test/…`, `chore/…`, `refactor/…` | Your short-lived working branches, created from `integration`. | You. |

- Name branches `<type>/<short-topic>`, for example `fix/stale-interest-expense` or `feat/share-link`.
- Keep branches short-lived and focused. Update from `integration` before opening the PR (`git fetch` then rebase or merge).
- Never push directly to `main` or `integration`.
- Pull requests are squash-merged into `integration`, so the PR title becomes the commit message. Make it count.
- Maintainers promote `integration` to `main` with a PR titled `release: <summary>`, tag it, and list what changed.

## Before you start

1. Look at **What's left to do** in the [README](README.md) and at open issues labelled `good first issue` or `help wanted`.
2. For anything bigger than a small fix, **open an issue first** and describe what you want to change and why. Items marked
   *(needs a decision)* in the README must be discussed before code is written.
3. Comment on the issue so nobody duplicates your work.

## Set up and test

See the [README](README.md) for setup. Before you open a PR, all of these must pass:

    python -m pytest              # unit tests
    python -m pytest -m e2e       # browser tests
    python -m pytest -m network   # only if you touched data providers; hits real services

Rules for tests:
- **Write the failing test first**, watch it fail for the right reason, then make it pass. This is how the project was built.
- Default tests must be deterministic and offline. Use the fake provider (`DCF_PROVIDER=fake`, `tests/fixtures/fake_world.json`,
  regenerated by `scripts/make_fake_world.py`) instead of real services.
- Recorded real payloads live in `tests/fixtures/yahoo_*.json`. Add a new one when a real company exposes a bug
  (`python scripts/record_fixture.py TICKER tests/fixtures/yahoo_<name>.json`).
- A bug fix needs a test that fails without the fix. A new behaviour needs a test that describes it.

## Code conventions

- Python 3.12, type hints on public functions, small focused modules.
- **Finance logic lives in `src/dcf` and is pure** (no network, no I/O) and unit-tested. The web page only renders:
  **no model maths in JavaScript.**
- **Money:** every monetary value on the page goes through `money()` in `src/dcf/web/format.js`. Never hard-code `$`, `€` or
  currency codes; a test guards this.
- **Safety:** never insert provider data with `innerHTML`; use the helpers in `src/dcf/web/dom.js`.
- Rates and percentages inside Python are percent points (`8.6` means 8.6%).
- No dead code and no commented-out code. Prefer deleting.

### Comments and docs

- Comment the **why**, not the what. If a line needs a comment to explain what it does, rewrite the line.
- Add a short docstring to every public function saying what it returns and any surprising rule.
- When you implement a finance formula or convention, **link the source** (a URL or a book chapter) in a comment or in the PR.
- Keep user-facing text plain and honest. The tool gives an educational estimate; wording must never read as a
  buy or sell recommendation.

## Changing the valuation model

Changes to how numbers are calculated need extra care because they change what users see. In the PR:
1. Explain the **source or reasoning** (a link to a recognised reference).
2. Add a **test vector** (inputs and the expected value, with the arithmetic or the source).
3. Show a **before and after** on at least one real company (for example "AAPL base $154 to $164").
4. Update the design spec in `docs/superpowers/specs/` and the "How the numbers are built" section of the README.
5. Add the `accuracy` label so reviewers know to look closely.

## Commits

Use [Conventional Commits](https://www.conventionalcommits.org/): `type: short imperative summary`.

| Type | Use for |
|---|---|
| `feat` | a new user-visible capability |
| `fix` | a bug fix |
| `docs` | documentation only |
| `test` | tests only |
| `refactor` | code change with no behaviour change |
| `chore` | tooling, dependencies, housekeeping |
| `perf` | speed improvements |

Write the body to explain **why**. Reference issues with `Fixes #12` or `Refs #12`. Keep commits small and each one green.

## Pull requests

- Target **`integration`**. The PR template (`.github/pull_request_template.md`) appears automatically; fill in every section.
- Title in Conventional Commit form, for example `fix: ignore non-finite beta from the data provider`.
- One concern per PR. Large PRs are hard to review and will be asked to split.
- Mark it **Draft** until tests pass and you want a review.
- For UI changes include a screenshot (desktop and phone width).
- Respond to review comments by pushing new commits (don't force-push over a review in progress).
- Maintainers aim to respond within a few days; it is best-effort, not a promise.

### Labels

Apply one label from each group that fits (maintainers will correct them). Suggested set:

| Group | Labels |
|---|---|
| Type | `bug`, `enhancement`, `documentation`, `tests`, `chore`, `question` |
| Area | `valuation-model`, `data-source`, `ui`, `api`, `ci`, `docs` |
| Status | `needs-triage`, `needs-discussion`, `blocked`, `wip`, `ready-for-review` |
| Priority | `P1-critical`, `P2-important`, `P3-nice-to-have` |
| Community | `good first issue`, `help wanted` |
| Special | `accuracy` (changes valuation numbers), `breaking-change`, `security` |

## Review

Reviewers check, in this order: does it do what the issue says; is it tested (and did the test fail first); is the
valuation reasoning sound and sourced; is it safe (no secrets, no injection, no hard-coded currency); is it readable.
Be kind and specific in reviews, and assume good intent. At least one maintainer approval is required.

## Security and secrets

- **Never commit API keys or tokens.** Keys come from environment variables; `.env` files are git-ignored.
- Found a security problem? Do **not** open a public issue. Use GitHub's private "Report a vulnerability" (Security tab).

## AI assistants

You are free to use Claude or any other assistant as you like. You are responsible for what you submit: it must meet
every rule on this page, and you should be able to explain it. Local assistant notes (such as `CLAUDE.md`) are
git-ignored and are not part of the project.

## Conduct and license

Be respectful and constructive. Harassment or personal attacks are not tolerated, and maintainers may remove comments
or contributors who cross that line. By contributing, you agree that your contribution is licensed under the
project's [MIT License](LICENSE).

## For maintainers: repository setup checklist

- [ ] Create the `integration` branch from `main` and push it.
- [ ] Set the default branch to `integration` so new PRs target it automatically.
- [ ] Protect `integration` and `main`: require a pull request, at least one approval, passing checks (once CI exists),
      and disallow force-pushes and deletions.
- [ ] Create the labels above (Settings → Labels, or `gh label create`).
- [ ] Enable private vulnerability reporting (Settings → Code security).
